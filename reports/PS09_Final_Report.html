Kernel Optimisation for Encoders · Theme: Pipeline Building · Submission file: team.py

How to read the numbers. Every figure is labelled as one of: measured (produced by a script in this repository; file named), CPU emulation (measured on a CPU, emulating GPU numerics), reported (from the teammate's tracker, not reproduced here), or estimate (calculated, not measured). Sections fed by result files are regenerated by scripts/make_report.py; anything not yet measured on the GPU is shown as PENDING.

1. Executive summary

The reference encoder (reference.py) runs BAAI/bge-base-en-v1.5 in FP32 and pads every input to 512 tokens. On the practice set the average passage has 100 tokens, so 80.4% of the reference's work is padding (measured, exact). Our team.py keeps the same weights, the same 12-layer architecture and the same maths, and changes only how the model runs:

  1. Length-aware scheduling (sort by length, token-budget batches, split at length buckets): token positions computed drop from 51.2 M to 10.4 M for 100k passages; with the CLS-only last layer the analytical work is 5.62x lower than the reference (measured, exact count).
  2. FP16 Tensor-Core GEMMs with an FP32 residual stream, fused QKV projection and PyTorch's fused SDPA attention.
  3. Overlapped host pipeline (tokenisation in a background thread, pinned memory, asynchronous copies, one sync).
  4. CLS-only last layer: the last layer computes keys/values for all tokens but everything else for the CLS row only.
  5. CUDA Graphs for live queries: one graph replay per query instead of hundreds of kernel launches.

Accuracy is protected by a precision gate (minimum cosine ≥ 0.9995 internally, 0.999 is the rule). A CPU precision study found that the worst cases are short passages and that keeping the residual stream in FP32 cuts the worst-case error several-fold at the cost of only element-wise work, so it is on by default.

GPU throughput, latency and profiler results: see Section 13 onwards (PENDING until the RTX 3050 runs complete).

2. Problem statement

A university library needs embeddings for millions of passages on one modest GPU. The model must stay BAAI/bge-base-en-v1.5 (no smaller model, no INT8, no weight or architecture changes). Each output must have cosine ≥ 0.999 to the FP32 reference on every input; a single violation scores zero. Scoring: batch throughput speed-up 50% (log scale, full marks at 40x), profiler report 25%, live-query p50/p99 15%, demo 10%.

The official harness (bench.py) calls setup() once (not timed), then encode(all_passages) once (timed end to end, including tokenisation), then replays a query trace in real time with encode([query]), one query at a time, FIFO, so latency includes waiting behind earlier queries of a burst.

3. Baseline architecture

reference.py: Hugging Face AutoModel in FP32, tokenizer with padding="max_length", max_length=512, batch 32, CLS token of the last hidden state, L2-normalised, .cpu() after every batch.

7. Objectives

  1. Never violate the tolerance (internal gate 0.9995 on the official references, and a full 100k check).
  2. Maximise offline throughput (passages/s on 100k passages, end to end).
  3. Minimise live p50/p99 under bursts.
  4. Collect before/after profiler evidence for each claim.

8. Proposed architecture

setup()  (not timed)  load weights -> FP16 GEMM weights, FP32 LayerNorm -> warm up at the real batch shapes
                      (largest first; halve the token budget if the GPU is too small) -> capture CUDA Graphs (32/64/128)

encode(texts)
 ├─ 1 text  -> tokenise -> copy into the static buffers of the smallest bucket -> graph.replay() -> [1,768]
 └─ N texts -> producer thread: tokenise 16k-text chunks (Rust tokenizer, no padding)
                 -> sort by length -> token-budget batches split at multiple-of-8 length buckets -> pinned tensors
             -> consumer (main thread): async H2D copy -> 12-layer FP16 encoder (fused QKV, SDPA, CLS-only last layer)
                 -> CLS -> FP32 L2-normalise -> scatter into a preallocated [N,768] GPU buffer in input order
             -> one device-to-host copy at the end

9. Optimisation methodology

ID Optimisation Bottleneck targeted Switch Stage
O1 FP16 Tensor Cores, fused QKV GEMM, PyTorch SDPA (flash / memory-efficient kernels), no pooler FP32 GEMMs, unfused attention PS09_FP16 S1+
O2 Sort by token length, token-budget batches, pad to a multiple of 8 padding (80.4%) PS09_SORT, PS09_BUDGET S2+
O2b End a batch where the padded length drops to a lower multiple of 8 (after ≥ 25% of the budget) residual padding inside large batches PS09_BUCKET S2+
O3 Background tokenisation, pinned memory, async copies, single final sync host stalls PS09_OVERLAP S3+
O5 CLS-only last layer 11/12 of last-layer work unused PS09_CLS_ONLY S4+
O7 CUDA Graph per live bucket (32/64/128 tokens) kernel-launch overhead for single queries PS09_GRAPH S3+
O4 torch.compile of the encoder element-wise kernel fusion PS09_COMPILE S5
P1 FP32 residual stream + LayerNorm (GEMMs stay FP16) FP16 rounding of the residual stream PS09_RES32 default on

Stages are cumulative presets (PS09_STAGE=0..5); each flag can be overridden alone for ablations. The submitted defaults are constants at the top of team.py; the organisers do not need to set any variable.

Rejected: padding-free variable-length attention (O6) - residual padding is only ~4% after O2/O2b, not worth the complexity; BF16 - fails the internal gate (Section 11); FP16 accumulation inside GEMMs - expected to break accuracy (measured on the GPU in validate_fp16_accum).

10. Mathematical correctness

  • Same weights, same graph. team.Encoder reads the checkpoint's tensors and applies exactly BERT's operations: word + position + token-type(0) embeddings → LayerNorm → 12 × [self-attention → output projection + residual → LayerNorm → GELU (erf) FFN + residual → LayerNorm] → CLS → L2 normalise.
  • Fused QKV concatenates the Q, K and V weight matrices row-wise; linear(x, [Wq;Wk;Wv]) is exactly [linear(x,Wq), linear(x,Wk), linear(x,Wv)].
  • Dynamic padding is exact: padded keys get an additive mask of the dtype's minimum (as in Hugging Face), positions start at 0 for every row (right padding), so the CLS output does not depend on how much padding a row has.
  • CLS-only last layer is exact: in the last layer the CLS output depends on the keys and values of all tokens (kept) but only on the CLS query, and the output projection, FFN and LayerNorms act row-wise, so the other rows are never needed.
  • Ordering: every batch carries its original indices; outputs are scattered into place on the GPU.
  • Truncation: the Rust tokenizer truncates at 512 tokens including [CLS]/[SEP], like the reference call.

Native torch.float16 kernels (CPU, tests/test_lowprec_cpu.py, the 8 worst passages + 5 others): plain FP16 min cos 0.999680, FP16 + FP32 residual 0.999960.

Findings: (1) the worst inputs are short passages (7-25 tokens), not long ones; (2) keeping the last layer in FP32 does not help - the error accumulates in the residual stream; (3) an FP32 residual stream with FP16 GEMMs reduces the worst-case error several-fold at the cost of element-wise work only; (4) BF16 (8-bit mantissa) is not accurate enough; (5) real FP16 kernels lose more than ideal rounding (native CPU FP16 0.999680 on passage #19 vs 0.999879 emulated, close to the 0.999663 the teammate measured on the GPU), which is why setup() also disables cuBLAS reduced-precision reductions. Maximum activation seen 16.4 (reported, GPU) / 15.8 (measured, CPU) against the FP16 limit of 65,504: no overflow risk.

12. GPU profiling methodology

profile_run.py wraps 2,000 passages in torch.profiler (CPU + CUDA activities) after a warm-up, exports a Chrome trace (trace.json.gz, open in ui.perfetto.dev), the top-30 operator table and a GPU-time split into GEMM / attention / norm + element-wise / memcpy / other, plus a device timeline analysis (busy fraction, idle gaps > 100 µs) and the CPU tokenisation time on its own. Throughput claims always come from the official bench.py, not from profiled runs. Peak memory: torch.cuda.max_memory_allocated in-process, and device-level nvidia-smi sampling around bench.py.

19. Limitations

  • GPU numbers are for an RTX 3050 Laptop GPU (6 GB); the organisers' GPU will give different absolute numbers. The code adapts (token budget halves automatically on a smaller GPU; graphs/compile fall back to eager if unsupported).
  • The reference baseline is a 5,000-passage sample. This is valid because the reference pads every input to 512, so its cost per passage does not depend on the text; the full 100k reference run (~1 h) was not repeated.
  • Official reference embeddings exist only for 2,000 passages; the other 98,000 are checked against our FP32 path, which itself matches the official reference (Section 18).
  • Live latency cannot use cross-query batching: bench.py calls encode with one query at a time, so the p99 under a burst is roughly the burst size times the per-query service time.
